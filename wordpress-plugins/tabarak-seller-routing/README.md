# Tabarak Seller Routing

## Seller to Driver app bridge

The outbound bridge was deployed to the linked Tabarak HUB project and configured on tabarakonline.com on 2026-10-14. A WordPress health check returned 11 active Driver app accounts. The database migration passed an isolated PostgreSQL fixture before deployment. A real customer order assignment has not been used as a smoke test; the Driver APK still needs the local customer detail changes released to show phone, address and GPS.

The Seller order detail now includes product image and SKU, including on a live offer, while customer details remain hidden until the branch claims the order. Staff may select **Served by** on the order detail before starting preparation.

Driver assignment uses the linked Supabase Driver app directory. Roll out in this order:

1. Apply `supabase/migrations/20261014000000_seller_driver_bridge.sql` to the Hub project.
2. Set a random secret of at least 32 characters as the Edge Function secret `SELLER_DRIVER_BRIDGE_SECRET`; deploy `supabase/functions/seller-driver-bridge` with JWT verification disabled. The function checks the separate secret header on every call.
3. In WordPress `wp-config.php`, define `TSR_DRIVER_BRIDGE_URL` as the HTTPS function URL and `TSR_DRIVER_BRIDGE_SECRET` as the same secret. Keep both off the mobile app and out of source control.
4. Check that Seller branch codes match Hub `branches.code`, that drivers have active `delivery_drivers` rows linked to Driver app accounts, and that their app is updated. Test one non-production order with a customer phone and GPS.
5. Release the updated Seller and Driver apps and plugin. The updated Seller app disables assignment when the bridge is absent; older clients retain the original WordPress-only path during rollout. A successful bridged assignment writes one idempotent Hub delivery order before WordPress confirms it, then the Driver app receives it through its active-order polling and an Expo push when a registered token exists. Earlier WordPress-only assignments need a separate reviewed backfill.

The outbound assignment bridge does not yet return pickup, delivered, or payment events to WooCommerce. The complete bidirectional lifecycle and durable retry outbox described in `HUB_BRIDGE.md` remain separate work; do not use Hub status as the WooCommerce payment truth until that is built.

This companion WooCommerce plugin owns Tabarak Online dispatch. Version 0.2.5 adds current Tabarak mobile order/payment/driver compatibility and bounded offer waves. Version 0.2.6 adds manager-only CSV imports for the active Tabarak Hub pharmacist directory (`code,name`) and its branch links (`branch_code,pharmacist_code`). Version 0.2.7 rejects expired offers at the API even when WP-Cron is late. The current Seller payload shows catalog name, SKU and image on an offer while keeping customer information and events hidden until a branch claims it. Version 0.2.8 adds an administrator-only action to retry an existing unassigned mobile order after routing is enabled. Version 0.2.9 prevents caching of the authenticated Seller API and lets an administrator retry an unclaimed order after its offers expire. Seller selection shows names, stores the matching code internally on the order, and does not send codes through customer order APIs. Version 0.2.16 starts preparation and records the selected pharmacist when a branch accepts an offer. Version 0.2.17 supports date range filters on Seller order history. Version 0.2.18 keeps orders active until the Driver app confirms delivery and shows only delivered orders in history. Automatic routing defaults to OFF.

## Setup

1. Open **WooCommerce → Seller Routing**. Use **Copy published Our Branches into routing** to load the branch directory directly, or export/download an Excel-compatible UTF-8 CSV, edit it in Excel, and import it. Imports update rows by stable branch code and never delete omitted branches. Repeating the directory copy updates contact details, locations, opening hours, and active state while keeping seller account links, payment flags, and pharmacist lists.
2. Click **Edit** beside a branch to change its routing settings. Review its block, precise coordinates, Bahrain hours, pharmacist roster, and payment flags. A copied branch missing a block is kept inactive until the block is supplied. Unrecognized directory opening hours also import as inactive. **Card** means eligibility to receive a confirmed Tap prepaid order, not the presence of a card terminal. Newly copied branches do not accept card by default; enable **Accept Card** only for actual Tabarak branches approved to fulfil these orders. A branch with **Receive offers from any block** joins the fallback wave even when distant. Distance itself has no maximum radius.
3. Under **Branch accounts**, verify that every branch code is correct and there are no username conflicts. An administrator can create missing accounts in one action. Each username is the official branch code in uppercase, such as `T001`; each new account receives a separate 28-character random password, the **Tabarak seller** role, and its branch ID. New branch accounts have no email address. The one-time CSV download contains the new passwords; store it privately and distribute each password only to that branch. Running the action again does not rotate existing passwords. A branch employee cannot use the public lost-password flow; an administrator can reset a linked account's password from **Branch accounts**, which downloads a new one-time CSV and invalidates that account's Seller API sessions. Do not put staff passwords in the mobile app.
   District Pharmacy (`D001`) is retired and excluded from routing, imports and branch-account provisioning. Its old database row is retained for historical references.
4. Configure the Seller app's `EXPO_PUBLIC_SELLER_API_URL` to `https://<your-site>/wp-json/tabarak-seller/v1` and build a development/release Android binary with your EAS project ID. Push delivery needs a real EAS project ID and device token. A live test with a physical Android device is required.
5. Enable automatic dispatch only after the branch and account data are checked. Arrange a reliable WordPress cron runner; WP-Cron traffic timing is not a guaranteed real-time queue.
6. Exclude `^/wp-json/tabarak-seller/v1/` from LiteSpeed Cache **Do Not Cache URIs** and purge any older cached Seller API entries. Authenticated order and notification responses must never be cached.

## Current order flow

- Both `created_via=tabarak-mobile` and the older `propharm-mobile` WooCommerce orders are routed. Card waits for the matching Tap gateway's confirmed payment; Tabarak wallet waits for the recorded full wallet amount and paid date, including on-hold orders awaiting prescription review. COD offers immediately.
- Same-block branch gets the first exclusive window. Otherwise offers go to nearest open/payment-compatible branches, plus branches flagged anywhere. After the first window, the next nearest branches receive offers. The nearby wave expires after the configured response window (default 180 seconds) and becomes an admin exception if nobody accepts. Rejecting every open offer advances immediately. An atomic database claim makes the first accepted branch the winner.
- Cancelled, failed, refunded, and completed WooCommerce orders close outstanding offers even if automatic routing was turned off after the offers were created. A claimed branch assignment stays visible in seller history, while closed-order actions are rejected.
- If no branch can accept, an exception stays visible in Seller Routing. Admin can assign an exception manually, subject to the branch's payment capability. A missing GPS location also becomes an admin exception.
- Branch staff select their pharmacist identity on Home or on an unprepared order, mark preparation/ready, and select a linked Driver app account after ready. Payment method, wallet-paid amount and due amount are exposed to staff.
- Claimed mobile orders show distinct WooCommerce workflow statuses: Accepted by branch, Preparing, Ready for pickup, and Handed to driver. These statuses track fulfillment without changing the separate payment record. Existing claimed orders sync to the latest saved Seller stage the next time Seller loads them.
- WooCommerce REST order responses also include `fulfillment_status` and `fulfillment_label`, independent of WooCommerce `status`/payment: `awaiting_branch`, `under_review_and_preparation`, `scheduled_for_delivery`, `delivered`, or `cancelled`. Customer apps should render these fields for the delivery timeline while continuing to read payment from the order payment fields. `seller-ready` remains under review/preparation until the Seller confirms handover to the driver.
- Accepted orders can be edited and assigned to a driver until a driver is assigned or delivery/handover closes the order. The driver picker lists all active Driver app accounts, sorts on-duty drivers first, and displays 12 drivers per swipeable page. The order breakdown shows item subtotal, discounts, shipping, fee lines, VAT, and rider tip before the order total.
- After an order is physically handed to a driver, branch staff press **Handed to driver** on its detail page. This writes one immutable handover snapshot per order to `tabarak_seller_handoffs`. Handover alone does not move an order to history: active orders keep it until the Driver app confirms delivery, and history contains delivered orders only. The Day/Week/Month/Year gross-sales chart still sums the stored order total in Bahrain time at handover, excluding orders later marked cancelled, failed or refunded. Date filters in history use delivery time. The handover snapshot stays available even if a WooCommerce order is later deleted. Orders handled before this action was introduced are not automatically classified as handed over. Until the Driver bridge status action is deployed, handed-over orders remain active and the Seller history shows no delivery confirmations.

## Not yet connected

- The outbound bridge is live for Seller assignment, but pickup/delivered/paid events still do not return to WooCommerce. The Driver app customer-detail changes need a new APK release. Do not give Supabase service credentials to the Seller mobile app.
- The customer mobile app source is not present in this workspace. Its order timeline must read WooCommerce REST `fulfillment_status` / `fulfillment_label` to show the branch workflow; if it reads a different endpoint, that endpoint needs the same fields. Branch cancellation with a reason and protected prescription access in Seller are also not implemented.
- Delivery duration, paid+delivered reconciliation, and per-driver tips in the dashboard remain unverified until that bridge is deployed and tested. The dashboard labels this gap rather than inventing metrics.
- The branch transfer and schema migration have local WordPress/WooCommerce integration checks. Card capture timing, cron timing, racing branch claims, notifications and cancellation still need production-like testing before automatic dispatch is enabled.

## Seller offer alarm

New offers play a 20-second custom Android alarm with a matching vibration pattern. WordPress schedules a reminder push every 30 seconds while the branch offer remains open; it stops after claim, expiry, or closure. Reminder timing depends on the site's WP-Cron runner and may be delayed when cron is not running.
