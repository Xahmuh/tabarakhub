# ADR: Scoped access and employee identity for Tabarak Hub

Status: Proposed. The foundation migration is additive; no production cutover is authorized by this document.

## Actual system and constraints

The running web app is React/Vite with a Supabase browser client, not a Next.js
server. `App.tsx` and `AppRouter.tsx` control navigation, while PostgREST/RLS and
Supabase Edge Functions control data access. `app_user_profiles`,
`role_permissions`, `app_user_feature_permissions`, `supervisor_branches`,
`branch_zones`, and branch staff assignments already exist. Creating a second
generic roles and permissions system would produce two conflicting sources of
truth.

Current gaps verified in source:

- Existing live TQPH policies may still authorize admin/owner/supervisor
  without branch scope. The prepared `20261018030000_tqph_branch_rls.sql`
  migration limits record reads and removes direct browser writes. The prepared
  atomic submission function validates supervisor assignment, the current
  checklist and appraisal scores, required CAPA tasks, and a verified reviewer
  name. Both migrations passed in a disposable PostgreSQL 18 fixture but have
  **not** been applied or validated against the live schema. The browser lists
  only permitted branches; database RLS must still be applied before this is
  a security guarantee. Historical records without a reviewer name snapshot
  cannot produce a PDF until reviewed. Real portal notifications remain a
  release blocker; the UI no longer claims they were delivered.
  CAPA resolution is paused because the old form accepted demo URLs or browser
  blob URLs as proof. The prepared RLS migration makes the evidence bucket
  private and blocks browser access until object paths can be tied to authorized
  audits or CAPA tasks. Re-enable only after a real upload, durable storage
  path, signed read URL and branch-scoped authorization are verified.
- `StaffPayrollHub` now reads database employees and approved deductions for a
  preview; transfer export is blocked. `DriverPayrollHub` still needs the same
  approval gate. Neither is a published, approved payroll run.
- HR requests store names/CPR but no Auth-to-employee identity. Old requests
  cannot safely be assigned to a personal inbox by matching a name.
- Custom roles in `roleRegistry.ts` are stored in localStorage and are not a
  database authorization source. The front end has permission checks, but
  direct Supabase requests bypass them.

## Decisions

1. Keep `admin` as the technical super-admin role and `accounts` as Finance.
   Payroll is a narrower financial boundary: only `owner` and `accounts` may
   view and approve company pay; only `owner` may edit salary. The legacy
   `manager` name stays only as a compatibility alias. Add an `employee` role
   with no module access until personal screens and RLS are ready.
2. Link each personal Auth account to exactly one `employees.id` through
   `app_user_employee_links`. Do this explicitly in Access Control. Never infer
   the link from name, CPR, email, or a shared branch login. Reuse existing
   `supervisor_branches` for supervisor scope and `app_user_profiles.branch_id`
   for branch logins. `employee_branch_assignments` describes staff placement.
3. Define every data operation by both action and scope. Role/feature grants
   decide whether the operation is allowed; RLS limits which rows it touches.
   The client may hide buttons, but the database remains authoritative.
4. Store a payroll deduction as an immutable proposal plus two immutable
   decisions: one from Owner and one from Accounts, by distinct Auth users. A
   security-invoker view exposes only proposals with both approvals. A reject
   leaves the proposal excluded. Published payslips are snapshots of a payroll
   run, created only by a server-side publication function after rechecking
   approved deductions; the employee sees only their own published snapshot.
5. Employee Inbox rows are generated by database triggers after an HR letter
   reaches Approved/Completed or a payslip is published. Store documents in a
   private bucket and serve short-lived signed URLs after an identity check.
   A database path is never a public download URL.

## Permission and scope matrix

| Actor | Modules | Data scope | Writes |
| --- | --- | --- | --- |
| Owner | Company payroll and salary | All employees | Edit salary and owner approval |
| Accounts | Finance, payroll approvals, operational expenses | All employees for payroll | Accounts approval; cannot edit salary |
| Admin / Manager | Operational administration | Branch scope by module | No payroll approval or salary edit |
| Supervisor | Dashboard, delivery, QA, codex, scheduler, leave, TQPH, feedback, contributions, attendance | `supervisor_branches` membership | Only allowed feature actions in assigned branches |
| Branch | Operational branch modules and branch TQPH rating | `app_user_profiles.branch_id` | Branch-scoped actions; no payroll |
| Warehouse | Shortages/stock/lost-sales dashboard | Network read for those features | Procurement actions only |
| Employee | Attendance, HR self-service, Inbox, personal TQPH | Linked `employees.id` only | Own requests, read own published documents |

Element-level permissions continue as `feature:action` keys in the existing
permission tables. They are not a replacement for row scope. New keys should
be seeded disabled, then enabled per role after data policies and UI are ready.

## Safe rollout sequence

1. **Inventory and baseline.** Run the read-only
   `supabase/audits/employee_rbac_preflight.sql` against the target project.
   Record current policy/grant definitions, row
   counts, branch IDs used by TQPH, Auth profile/employee mapping candidates,
   existing HR status values, and current payroll outputs. Reconcile mock TQPH
   IDs with production UUIDs. Confirm backups and a rollback deployment.
2. **Additive schema.** Apply `20260930024007_rbac_employee_foundation.sql` in
   staging first. It adds nullable HR identity fields and new isolated tables,
   without changing old module reads or deleting data. Validate grants, RLS,
   policies, indexes, and trigger behavior with Admin, Finance, branch,
   supervisor, employee, and unrelated users. Keep new feature grants `none`.
3. **Identity staging.** The admin-only Edge Function validates the target
   employee and stores a pending email/employee mapping, but creates no Auth
   principal or password. An inactive application profile is not sufficient:
   a Supabase Auth session could still reach legacy policies that grant reads
   to every `authenticated` user. A database trigger blocks premature employee
   role assignment. After the old policies and self-service screens pass the
   access matrix, remove that guard in a reviewed migration and create Auth
   accounts for one pilot at a time via an approved invite channel. Reconcile
   old HR requests manually; never mass-link by text fields.
4. **Database scoping, one module at a time.** Add RLS policies for TQPH,
   attendance, HR, feedback and payroll, including child tables and storage.
   Start with a shadow query in staging and compare authorized row counts.
   Remove mock fallback on authorization errors. Keep the previous deployment
   available for immediate Vercel rollback; a frontend rollback cannot undo
   restrictive database policies, so policy rollout needs its own reverse SQL.
5. **Payroll gate.** Ship proposal/decision UI for Owner and Accounts. Convert
   both staff and driver attendance penalties from immediate subtraction into
   proposals. Only approved rows enter server-calculated payroll. Validate the
   transfer export and payslip against the same saved payroll run. Do not
   publish payslips before a run is frozen and approved.
6. **Personal modules.** Enable employee login, HR request tracking, Inbox,
   personal attendance and pharmacist TQPH. Branch TQPH shows its own locked
   evaluations only. Supervisor UIs pass branch filters for speed; RLS enforces
   the same scope even if a request is edited in the browser.
7. **Progressive activation.** Pilot one branch/employee, audit denied access
   attempts and request latency, then expand by zone. Remove old broad policies
   and localStorage-only authorization only after all readers use the new path.

## Guards and verification contracts

There are no Next.js API routes in this repository. For every new Edge
Function, verify the bearer token with Supabase Auth, load the active
`app_user_profiles` row from the database, verify action permission and branch
or employee scope, then use the service-role key only for the authorized
operation. Do not trust `role`, `branchId`, `employeeId`, or financial amounts in
the request body as proof of permission. RLS must independently protect any
table that the browser queries directly.

Release gates: role/scope matrix tests (allowed and denied cases), migration
validation in staging, matching payroll totals with zero unapproved automatic
deductions, document URL authorization tests, TypeScript/test/build checks,
and smoke tests of current branch, supervisor, admin and finance workflows.
The TQPH submission UI now calls `submit_tqph_evaluation` so the audit,
appraisal and CAPA inserts succeed or fail as one database transaction. Apply
`20261018020000_tqph_atomic_evaluation.sql` and then
`20261018030000_tqph_branch_rls.sql` in staging, after the RBAC foundation.
The local SQL fixture verifies server score calculation, branch scope, evidence
closure, rollback and locked-row immutability. Live migration reconciliation and signed-in role
tests remain required. Until the migrations are applied, submission displays
the RPC error and does not claim success.
Production changes should be sequenced schema → backend → UI → feature grants.

## Accepted trade-offs

Keeping existing role tables reduces migration risk but requires cleaning up
legacy aliases and localStorage custom roles later. A single `employee` role
keeps authorization simple; employee category in the linked `employees` row
controls whether the personal TQPH view appears. Published payslip snapshots
add storage but keep each employee's monthly statement stable after payroll
settings change.
