# Supabase database audit — 2026-09-30

## Scope and method

Read-only inspection of the linked production database through `supabase db query --linked`, `supabase db advisors --linked`, PostgreSQL catalogs, row counts for selected candidates, and application references in this checkout. Database observed at 2026-09-30 03:11 UTC (PostgreSQL 17.6). No data, schema, Auth setting, or Storage object was changed. The direct migration-list connection failed because `SUPABASE_DB_PASSWORD` did not authenticate, so applied migration versions were read from `supabase_migrations.schema_migrations` through the Management API instead. Usage conclusions refer to this repository; external clients and scheduled jobs still need verification before deletion.

Inventory: 119 `public` tables, 4 views, 120 `public` functions, 323 indexes, 234 RLS policies, and 5 Storage buckets. All 119 `public` tables have RLS enabled. All four views have `security_invoker=true`. PostgreSQL statistics date from 2025-12-08, so index scan counts are historical, not a recent-use measure.

## Findings, in priority order

| Priority | Finding and evidence | Action before any deletion/change |
| --- | --- | --- |
| Critical | `public.branches` has `anon` SELECT and two public SELECT policies with `USING (true)` (`Allow reading branches`, `Public Read`). All 23 branch rows are active and exposed through the table grant, including columns such as `whatsapp_number`, `nhra_license_no`, `cr_number`, and `branch_manager_name`. `branches_clean` exists and deliberately hides these, but current application code still queries `branches` directly, including `services/branchService.ts` and public spin paths. | Define exactly which branch fields must be public; switch public clients to a safe projection/RPC, then remove broad anonymous table access and redundant policy after testing public flows. Do not drop `branches`. |
| High | `public.app_driver_resolve_login_identifier(text)` is an anonymously executable `SECURITY DEFINER` function. A valid active driver code returns the driver's email from `auth.users`; an invalid code raises a distinct error. The mobile login at `apps/driver-mobile/src/lib/api.ts:296` uses it. This allows code enumeration and email disclosure. | Redesign the login lookup to avoid revealing email/account existence, and apply rate limiting; test mobile sign-in before altering execute grants. |
| High | `public.legacy_branch_password_backups` contains 22 nonempty `legacy_password` values, captured 2026-06-12. It has RLS and no anonymous/authenticated policy or grants, but retaining old credentials creates exposure if privileged access or backups leak. It has an FK to `branches`; project documentation notes a legacy branch row depends on it. | Determine whether passwords are still valid, rotate any valid ones, export to controlled retention if required, then request explicit approval for removal of this backup and its dependent legacy branch row. Never paste password values into reports. |
| High | The latest applied migration in the live database is `20260929233239`; this checkout also contains the uncommitted `20260930024007_rbac_employee_foundation.sql` and related code changes. The new RBAC design is therefore not deployed to this linked database. | Finish the RBAC rollout checklist and validation before deploying the code that depends on it. Keep this audit separate from that in-progress work. |
| Medium | Nine constraints are `NOT VALID`: 3 role/scope checks, 4 delivery-order FKs, 1 role-permissions check, and 1 workflow-template date check. A read-only spot check found one `branches` row whose role is not `branch`; zero violations for checked profile/permission roles and four delivery FK relationships. Existing invalid rows can prevent later validation and undermine assumptions made by application code. | Identify and classify the one legacy branch record, reconcile it, then validate constraints individually in a planned migration. Verify `workflow_task_templates_ends_on_check` and all constraints again just before validation. |
| Medium | Supabase advisors report 9 anonymous and 69 authenticated callable `SECURITY DEFINER` functions; the anonymous set includes public spin/review RPCs that may be intentional. They also report 148 overlapping permissive-policy cases and 11 RLS initplan warnings. These are advisor findings, not 237 confirmed vulnerabilities. | Review each function's input checks, side effects, and grants; prioritize the driver lookup and public spin RPCs. Consolidate overlapping policies after behavior tests; profile the 11 RLS expressions on affected queries. |
| Medium | Supabase Auth advisor reports leaked-password protection disabled. | Enable and test it in Supabase Auth settings after reviewing user sign-in impact. |
| Low | Several indexes show zero recorded reads despite nontrivial size, including `delivery_notifications_branch_created_idx` (288 KiB), `delivery_pickup_batches_branch_started_idx` (256 KiB), `idx_delivery_orders_target_branch_id` (176 KiB), and `idx_delivery_orders_order_type` (176 KiB). The 416 KiB `benefit_pay_transfers_serial_number_key` is a uniqueness constraint and should not be treated as disposable. | Check actual query plans, constraint backing, and peak-period workload before removing any index. The zero-scan statistic alone is insufficient. |

## Explicitly keep

`branches`, `delivery_orders`, `benefit_pay_transfers`, `delivery_order_audit_logs`, `quality_feedback_questions`, `lost_sales_excel_export`, and `delivery_orders_clean` have current runtime references or operational/audit data. `operational_renewals` currently has zero rows but is used by `services/operationalRenewalService.ts`; do not infer it is obsolete from its row count.

## Limits and safe next step

This audit did not inspect deployed Edge Function versions, external API consumers, database query logs, Auth user sessions, cron definitions, PITR/backup retention, or every row of every table. Before approving a specific deletion, check inbound SQL dependencies/triggers and external use, capture a restorable backup, prepare a migration with rollback, and test the affected application paths. No DROP/DELETE/REVOKE was run.
